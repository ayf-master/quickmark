# 02 · 前端架构与状态管理

> 目标：理解 QuickMark 没有用 Pinia，而是用一个「全局 reactive 单例」做状态中枢。这是全应用数据流的核心。

## 2.1 为什么不用 Pinia

项目早期规模小，引入 Pinia 反而增加样板。Vue 3 的 `reactive()` 本身就够用：导出一个模块级单例对象，任何组件 `import { store }` 就能读写，响应式自动生效。本质是「手写版迷你 Pinia」。

```js
// src/store/index.js（精简示意）
import { reactive, computed, watch } from 'vue';

const store = reactive({
  // —— 数据 ——
  notes: [],
  categories: [],
  editingNote: null,
  editTitle: '',
  editContent: '',
  editCategoryIds: [],
  editLinks: [],
  editPlanData: null,
  editMode: 'markdown',

  // —— UI 状态 ——
  sidebarWidth: 240,
  listWidth: 320,
  knowledgeGraphVisible: false,
  imagePreviewVisible: false,

  // —— 导航历史（栈）——
  noteHistory: [],
  noteForward: [],

  // —— 方法（写在对象里，this 即 store）——
  async loadAll() { /* ... */ },
  openNote(note, options) { /* ... */ },
  async saveCurrentNote() { /* ... */ },
  scheduleAutoSave() { /* ... */ }
});

export { store };
```

组件侧：

```js
import { store } from '@/store';
// 模板里直接 {{ store.editTitle }}
// 脚本里直接 store.openNote(n)
```

**原理**：`reactive()` 用 Proxy 包裹对象，读属性时收集依赖、改属性时触发更新。模块单例确保「全应用同一份状态」，某个组件改了 `store.notes`，所有用到它的组件自动重渲染。

## 2.2 关键 computed：派生数据

`reactive` 对象里可以挂 `computed`（注意 `computed` 返回的是 ref，要包一层对象或用 `get`）。本项目把派生数据写成「返回 computed 的方法」或直接定义在 store 上：

```js
// 分类树：把扁平 categories 按 parentId 嵌套，再按 position、中文名排序
const categoryTree = computed(() => {
  const map = new Map();
  const roots = [];
  for (const c of store.categories) {
    map.set(c.id, { ...c, children: [] });
  }
  for (const c of store.categories) {
    const node = map.get(c.id);
    if (c.parentId && map.has(c.parentId)) map.get(c.parentId).children.push(node);
    else roots.push(node);
  }
  const sort = (arr) => {
    arr.sort((a, b) => a.position - b.position || a.name.localeCompare(b.name, 'zh'));
    arr.forEach(n => sort(n.children));
  };
  sort(roots);
  return roots;
});

// 过滤后的笔记：搜索 + 收藏筛选 + 当前分类
const filteredNotes = computed(() => {
  let list = store.notes;
  if (store.selectedCategoryId) {
    list = list.filter(n => (n.category_ids || []).includes(store.selectedCategoryId));
  }
  if (store.showPinnedOnly) list = list.filter(n => n.is_pinned);
  const q = store.searchQuery.trim().toLowerCase();
  if (q) list = list.filter(n =>
    (n.title || '').toLowerCase().includes(q) ||
    (n.content || '').toLowerCase().includes(q));
  return list;
});
```

**要点**：派生数据集中到 store，组件只消费 `store.filteredNotes`，不必每个组件各算一遍，避免不一致。

## 2.3 链接索引与知识图谱数据

`graphData` 是一个 computed，扫描所有笔记正文里的 `[[笔记名]]` wiki 链接，构建「节点 + 边」，供 `KnowledgeGraph.vue` 直接用：

```js
const linkIndex = computed(() => {
  const idx = new Map(); // title -> [noteId...]
  const edges = [];
  const re = /\[\[([^\]]+)\]\]/g;
  for (const n of store.notes) {
    const text = n.content || '';
    let m;
    while ((m = re.exec(text))) {
      const title = m[1].trim();
      if (!idx.has(title)) idx.set(title, []);
      idx.get(title).push(n.id);
    }
  }
  return idx;
});
```

## 2.4 watch 驱动自动保存

`store` 里对编辑字段做 watch，任何改动触发 1s 防抖保存：

```js
watch(() => store.editTitle,  () => store.scheduleAutoSave());
watch(() => store.editContent, () => store.scheduleAutoSave());
```

`scheduleAutoSave` 见 `knowledge/07`。这里只需记住：**状态变更 → watch → 防抖 → API 写库**，用户无感知。

## 2.5 方法里的「快照」防坑

异步方法里有个高频坑：组件 A 在 `await` 期间，用户切到了笔记 B，`store.editingNote` 已经变成 B。若方法在 `await` 之后才读 `store.editTitle`，就会把 B 的标题写进 A 的库。本项目的统一解法是**在 await 前快照**：

```js
async _persistCurrentEdit() {
  if (!store.editingNote?.id) return;
  const noteId = store.editingNote.id;            // ✅ await 前快照
  const snapTitle = store.editTitle || '无标题';   // ✅
  const snapCategoryIds = [...store.editCategoryIds]; // ✅ 拷贝数组
  // ... 之后才 await API.updateNote(noteId, { title: snapTitle, ... })
}
```

`openNote` / `saveCurrentNote` / `closeEditor` 都用同一套路。这是本项目最重要的工程经验之一，面试讲到「并发状态一致性」时可以展开。

## 2.6 本篇知识点小结

- 全局状态 = 模块级 `reactive()` 单例，组件 `import { store }` 即用。
- 派生数据（分类树、过滤列表、图谱数据）集中为 `computed`，避免重复计算。
- `watch(editX) → scheduleAutoSave` 实现无感自动保存。
- 异步写库**必须先快照 id/标题/分类**，防止切换笔记导致状态串台。
